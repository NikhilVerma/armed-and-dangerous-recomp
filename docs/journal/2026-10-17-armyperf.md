# 2026-10-17 agent-armyperf: the marching army as crowds, and the 4K floor

Branch agent-armyperf (from wip/full-decomp c1661db). Target dirs engine/target-wt-armyperf (the build),
target-wt-armyperf-trace (`--features bevy/trace_chrome`, measurement only), target-wt-before (the unchanged build's
exe, for before / after runs). The machine was shared all session: 2-5 other agents' games running, often builds too.

## 1. The marching army

The original (src/ai/ai_07.cpp FakeGrunt_Update 0x00446460): a platoon's members are particles, one per ref point
of the platoon model, from pool 2 of Game+0xa90 (Particle_Alloc 0x0046d950): a 16-unit sprite (half-extent 8) with
the grunt picture of n_fx_bank_2 (uv u 0..0.25, v 0.625..0.875; captains u 0.25..0.375, v 0.51..0.624), white,
alpha 1, life ~3e7 s, placed on its point each update. A member becomes a real grunt only at the release (one every
0.1..0.2 s while the live army grunts are under the limit Game+0xbf0); the pool's 2000 particles (shared with effects)
capped the members: a platoon created with the pool full kept only what it got (+0xb68). army.rs already had these
rules; the port drew each member as a rigged low-detail grunt (~70 entities).

Now engine/src/crowd.rs (CrowdPlugin, game-neutral): a (model, anim) pair is baked once per level into a flipbook
(CPU skinning of the run cycle at 30 frames per second of anim time; parts sharing a material merged: grunt_3 = 2
meshes); a `CrowdMember` is one entity (+1 child for the second part) that shows its phase's frame; members share
meshes and materials (instanced). The pose rate drops with distance (150 / 400 units: 30 / 15 / 10 fps) and a member
out of view keeps its pose: each frame change is a Mesh3d swap the renderer re-extracts. skin.rs gained
`Anim::pose` and `Skeleton::model_matrices`. army.rs: members spawn as crowd members (pace drawn as before), and
fake_hits gathers the player's shots once, inverts the platoon matrix once and rejects shots outside a sphere round
the box and members (results unchanged: same kills).

Measured (headless, turret on the army, `ENTDBG=1`; before = target-wt-before, same scripts):

## 2. The 4K floor

Profiled with a chrome trace of the bench (summed per span by a streaming script in the scratchpad: the trace is
~2 GB per 10 s). The one large waste: `allocate_and_free_meshes` 1.4 ms median every frame, from the three particle
pool meshes rebuilt each frame; Bevy packs a changed mesh's attributes into mapped GPU memory one vertex attribute
at a time (strided writes; with a position-only mesh the same uploads took 0.10 ms). Fixed: the pool mesh only
numbers its corners and keeps a power-of-two size; particle.wesl's vertex shader reads the corners from a
`ShaderBuffer` that Bevy updates in place (one contiguous write). Empty streamer meshes are no longer rewritten.
`--profile` now records meshes_changed / mesh_vertices_changed (bench: 5.8 / 8.6k per frame -> 0.5 / ~100).

Bench (`--bench 20 --size 3840x2160 --background --preset remaster --profile`), before / after alternated, with 2-3
other agents' games running and no builds:

| | fps avg | 1 % low | render CPU | main CPU | GPU |
|---|---|---|---|---|---|
| before | 116.9 / 115.8 / 116.7 | 81 / 92 / 99 | 5.9 / 6.4 / 5.8 | 3.3 / 3.6 / 3.2 | 2.4 / 2.8 / 2.4 |
| after | 116.4 / 117.7 / 117.3 | 91 / 98 / 98 | 5.7 / 5.1 / 5.1 | 3.6 / 3.2 / 3.2 | 2.9 / 2.6 / 2.4 |

Both builds run into the driver's ~119 fps cap (median frame 8.41 ms) on this machine when it is not saturated; the
uncapped estimate (slowest stage) is ~5.3 ms after vs ~6.2 before. The 96.9-98.9 fps of the corpses journal were
measured with the CPU saturated (with 5 other games plus builds both builds gave 62-84 fps here). So the floor holds
with the Remaster defaults; nothing was turned down.

## Open

- Render CPU left (trace): prepare_preprocess_bind_groups ~1.2 ms (Bevy rebuilds the preprocessing bind groups per
  view and phase each frame), write_binned_instance_buffers ~0.8 ms each for the opaque and prepass phases, queue
  submit ~1.5 ms.
- Streamers with live trails still rebuild their mesh (4 attributes) every frame; the particle path (a corner
  buffer) would fit them too.
- `PlayState` exists in normal play, so every `log_*` state system builds its JSON each frame (~0.3 ms main).
- The members could animate in the vertex shader (phase and pace per instance, no mesh swaps), but the game
  material's prepass must then animate the same way (docs: never give the game material a prepass shader of its own);
  not done.
- The original's sprite look for the Original preset (pool-2 particle per member) is not offered; the crowd mesh is
  used in both presets.
