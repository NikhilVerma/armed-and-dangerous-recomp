# 2026-10-17: tests that failed only on a loaded machine (agent-flaky)

Branch agent-flaky (from wip/full-decomp 211d2a2). Remaster built in engine/target-wt-flaky; every run --background.
Load for the checks: 4 copies of defence_l5m5 in a loop (plus 2-5 other agents' engine runs), the affected tests run
with tools/regress.py meanwhile.

Scripted runs already stepped game time by a fixed 1/60 s a frame, so the game itself should not care how fast the
machine is. It did, in four places. Evidence for each: the baseline exe (211d2a2) failed under the same load, and the
fixed one gives identical sound logs (`--env AND_SOUND_LOG=FILE`) from run to run.

## Cause and fix per test

- **audio_voice** (q1154014_ambient started at 9.3 s; baseline: also channel 0 empty at 3.52 s). A voice ended when
  its Bevy sink drained, which is the output device's wall clock. Under load the game ran at about 0.4x real time,
  so jon54013_ambient (4.9 s) ended after ~2 game seconds, its follow-on q1154014 was requested and started a frame
  before the scripted jon50062_dead took the channel. Fix (audio.rs): a one-shot ends when its length (the bank's
  `duration` / playback rate) has played in game time (`Voice::length`, age counted in unpaused game time). The
  voice also ages from its request, its file loaded or not (before, it waited for the asset server: a load-dependent
  number of frames); a file that loads late starts at the voice's age (PlaybackSettings `start_position`, read when
  the sink is made; a first version used `try_seek`, which blocks until the audio thread answers: audio_music froze
  at 12 s until the 1200 s limit). This is the original's behaviour in real
  time (the voice plays from the play call to the end of its data) and no longer depends on the device.
- **audio_stopall** (music not playing at 2.5 s, not paused at 3.3 s): the same cause. The music segment's voice was
  despawned when the device drained it, before the music system's game-time segment timer moved on.
- **gunner1** (turret.near false at 18.3 s; baseline failed 1 of 2 under load): two causes. (1) The AI reads whether
  a character's scream / line still plays (`PlayingVoices`: taunts, death lines) and draws random numbers on it, so
  the device clock changed the random stream. Fixed with the voices above. (2) Run to run, even then, the sound logs
  diverged at 14.7 s: fx debris (exp_wood_*, imp_rock_*) in a different order and variant. FxVm kept its fx objects
  in a `std::collections::HashMap` (randomly seeded per process) and updated them in that order, each drawing from
  the shared random stream. Now a BTreeMap by entity (fxvm/mod.rs). Same family, found by an audit of every std
  hash collection iterated in game code: badguy blast impulses were applied in the bodies map's order (fx.rs; now
  sorted by entity / body) and a camera path took the anim file's first camera in hash order (campath.rs; now the
  first by name).
- **infantry_l4m2**: the AI voice checks and the fx order above; 3 runs under load, identical sound logs (1480 lines).
- **defence_l5m5** (300 s timeout): deterministic (identical sound logs, 12870 lines), but its 66 game seconds take
  280-360 s of wall time on a loaded machine. playtest.py's default 300 s limit killed it. regress.py now gives each
  script 1200 s: the limit only guards against a hung game.
- **restart_parity** (dt_max_ms / main_ms / frame_ms): those are wall-clock measures of the machine, not of the game.
  They moved to `"expect_perf"` steps (playtest.rs), checked only when AND_PERF=1, i.e. `python tools/regress.py
  --perf` (PERF list: restart_parity) on an idle machine, and logged `EXPECT SKIP (perf)` otherwise. The parity
  checks (counts, camera, entities "as fresh") stay in the SUITE.
- Also (no reported failure): the level settle after a restart waited for five wall-clock frames under 100 ms
  (levelreset.rs). Game time runs while loading, so a loaded machine changed how many game frames a restart took. In
  stepped runs every frame now counts as calm (min_frames frames); real-time play keeps the wall-clock rule.

## Verification

- Baseline exe under load: audio_voice FAIL 2/2, audio_stopall FAIL 2/2, gunner1 FAIL 1/2.
- Fixed exe under load, 5 rounds of audio_voice, audio_stopall, gunner1, restart_parity, infantry_l4m2,
  defence_l5m5: 30/30 ok (4 to 9 engine processes running).
- Determinism: gunner1 x3, infantry_l4m2 x3, defence_l5m5 x2 under load: identical sound logs.
- Final build (start_position, not try_seek), under load (3 defence_l5m5 copies + other agents, 5 to 8 engines):
  5 rounds of audio_voice, audio_stopall, audio_music, gunner1, restart_parity, infantry_l4m2, defence_l5m5: 35/35 ok.
- Full `python tools/regress.py --exe target-wt-flaky` (final build, run under the same load): 101/101 ok, exit 0.
- level_smoke: 24 of 24 levels load and play. oracle_suite `--only remaster` against the stored original traces
  (ORACLE_OUT=work/oracle-flaky): 17/17 PASS. (Both ran on the try_seek build; the final change touches only a
  late-loaded voice's start offset.)

## Left / open

- Movies: the movie clock waits up to 0.5 s of game time for its soundtrack's sink, and the logged audio_time / drift /
  rate follow the device. Bounded, and the movie scripts check ranges that cover it; a preloaded soundtrack would make
  it exact.
- The rule for later work (docs/remaster-engine.md "Tips and traps"): a failure that only shows on a loaded machine is
  a wall-clock dependency to find, not "load".
