# Renderer interface (`src/rhi`)

Status 2026-10-04: boundary complete for D3D9. With `[render] rhi=1`, every GPU call the game makes goes
through `rhi::`. The D3D9 backend gives identical frames in all comparison scenarios
(`tools/compare.py --rhi`, run by `tools/check.ps1`), and no method falls back to D3D9 outside the interface
(the facade logs `outside the renderer interface` if one does).

## Layers

```
game code -> renderer (src/renderer, recovered, vtable 0x00589990) --+
statically linked D3DX (0x0054xxxx, e.g. D3DXLoadSurfaceFromMemory) -+-> D3D9 COM facade -> rhi::Device -> backend
```

### 1. The game's renderer

- The game reaches the renderer only through its vtable at 0x00589990: 129 slots (`tools/vtable.py`).
- It also creates objects the renderer hands out: vertex-buffer sets, index buffers, draw states.
- No code outside 0x004fb000-0x0050d000 touches the device (+0x14cc) or IDirect3D9 (+0x14c8). The only
  direct calls into the range are the factory (`Renderer_Create`) and unrelated zlib, sound and wave code
  linked there.
- Renderer bookkeeping that game code may read (fields of the Renderer object) therefore stays shared by
  every backend. Only the GPU work changes.

### 2. The D3D9 facade

Files: `src/rhi/d3d9_facade.cpp`, plus `d3d9_facade.gen.inl` generated by `tools/gen_d3d9_facade.py` from the
SDK's `d3d9.h`.

- **Shape:** 15 COM classes with 297 methods. The game, and the D3DX code inside the executable, call these
  instead of D3D9.
- **Routing:** the methods the game uses (the `ROUTED` list) call `rhi::`. Any other method falls back to the
  backend's D3D9 object if there is one, and is logged.
- **Identity:** an `rhi` object maps to one wrapper while the game holds references through it, so pointer
  comparisons in game code keep working. Reference counts mirror the `rhi` object's.

### 3. `rhi::` (`src/rhi/rhi.h`)

- **Contents:** Adapter, Device, Texture (2D and cube), Surface, Buffer (vertex and index), VertexLayout,
  VertexShader and PixelShader. All are reference counted like COM.
- **Size:** 73 operations. 68 were measured with `[test] rhi_calls=1` over every comparison scenario. Five
  more are called only by recovered code the scenarios don't reach: CreateOffscreenPlainSurface, SetLight,
  LightEnable, SetMaterial and SetLOD.
- **Vocabulary:** D3D9's enums and structs are used as plain value types (formats, render, texture-stage and
  sampler states, D3DPRESENT_PARAMETERS). They are the game's own description of its state.

### 4. Backends

- `rhi::d3d9` (`src/rhi/d3d9/backend.cpp`): one-to-one pass-through. This is the oracle.
- `rhi::vulkan`: next (docs/goals/modern-renderer.md step 3).

## What the game uses (the Vulkan backend's job)

| Area | Operations |
| --- | --- |
| Adapter | modes (GetAdapterModeCount, EnumAdapterModes, GetAdapterDisplayMode), CheckDeviceFormat, CheckDepthStencilMatch, caps, CreateDevice |
| Frame | BeginScene, EndScene, Clear, Present, TestCooperativeLevel, Reset, SetGammaRamp, GetAvailableTextureMem, EvictManagedResources |
| Resources | 2D and cube textures (levels, surfaces, LockRect), vertex and index buffers (Lock with NOOVERWRITE/DISCARD), off-screen surfaces, StretchRect, back buffer and depth surface |
| Targets | SetRenderTarget, SetDepthStencilSurface, SetViewport |
| Fixed function | SetTransform, SetMaterial, SetLight, LightEnable, render states, texture-stage states (the colour-mix combiners from Material_InitCombiners), sampler states |
| Shaders | vs/ps 1.x-2.0 bytecode from `shaders.dat` and the named pixel shaders. Constants c0-c95 (vertex) and c0-c7 (pixel) |
| Draws | SetStreamSource, SetIndices, DrawPrimitive and DrawIndexedPrimitive (triangle lists and strips; skin meshes are strips: docs/formats/big-skin.md 3.4) |

## Next

- **Scene description:** a per-frame stream built from the same calls, independent of D3D9:
  - camera from the view and projection transforms
  - lights
  - per draw: mesh (buffers plus layout), material (textures plus combiner state) and bone matrices (vertex
    constants)

  The Vulkan backend's depth, motion-vector and normal outputs, and later ray tracing, read from it.
- **Unexercised paths:** recovered paths no scenario runs yet (display-mode change, saving, debug overlay;
  see tools/coverage.py) may still use methods outside the list. They will log if they do.
